# Canvas: график по отбору модели из SQL-шагов — дизайн

**Дата:** 2026-09-21  
**Проект:** ARMGov-Dashboard (прототип проверки гипотез)  
**Основание:** экран «Аналитика по запросу» (`POST /api/ai/sql`); согласовано в обсуждении — вариант 2  
**Статус:** согласовано в обсуждении; ждёт утверждения файла перед планом реализации

## 1. Задача

Текст ответа агента и столбики на холсте обязаны говорить про одних и тех же людей (или категории). Сейчас датасет собирается из **последнего** успешного SQL целиком. Модель в тексте уже отфильтровала результат, а график этого отбора не знает.

Два живых прогона:

1. Сравнение Босова и Иванова. SQL по `ILIKE '%Иванов%'` вернул шесть строк (включая «Концева Надежда Ивановна»). Текст сравнил только Босова (629) и Иванова Ивана Ивановича (195). График показал всю выборку.
2. Тот же вопрос, два SQL. Первый нашёл только Босова (972). Второй — топ по `%иванов%` (Иванов Иван Иванович 51730 и ещё девять однофамильцев/отчеств). Текст: Иванов 51730 vs Босов 972. График — только второй запрос, **Босова нет**.

Нужно: модель указывает *кого* оставить; числа по-прежнему из фактических строк SQL, в том числе из **предыдущих** шагов того же прогона.

## 2. Решения по объёму (согласованы)

| Развилка | Решение |
|---|---|
| Откуда числа | Только из строк SQL-результатов этого прогона. Модель числа не пишет и не правит |
| Как выбрать строки | Поле `chart.keep`: точные подписи, как в таблице шага |
| Где искать | Все успешные SQL-шаги прогона, с конца (последний матч побеждает) |
| Нет `keep` | Как сейчас: весь последний SQL (рейтинг, топ-N) |
| `from=tool` / `preload` | Вне объёма v1 |
| Парсинг текста ответа | Нет |
| Клиент `charts.js` | Не меняет контракт: получает уже урезанный `dataset` |

## 3. Ограничения

- Только `SELECT`. Сборщик датасета не ходит в БД второй раз: работает по уже исполненным шагам.
- Цифра на графике = цифра в той строке SQL, которую модель назвала в `keep`. Если в тексте другое число, чем в строке, — это ошибка модели в тексте, график не подстраивается под прозу.
- Имена в `keep` копируются из результата **как есть** (`Иванов Иван Иванович`, не `Иванов Иван`). Совпадение точное, без `ILIKE`, чтобы «Ивановна» не попадала в график про Иванова.
- Архитектура прототипа не меняется: логика в `SqlAgentAsk` / сборщике датасета в `Program.cs`.

## 4. Компоненты

```
Program.cs
└── SqlAgentAsk
    ├── sqlResults[]     — каждый успешный sql-шаг: cols, types, rows
    ├── разбор chart.keep в action=answer
    └── DatasetFromSqlKeep(sqlResults, columns, keep, hint, limit)
         └── иначе DatasetFromSqlResult(последний sql) — поведение без keep

Промпт AgentSystemPrompt — когда обязан заполнить keep

tests (без модели) — сборщик keep по фикстурам двух sql-шагов
tests/smoke.py — контракт: keep в protocol шага answer, если задан
```

Клиент не читает `keep`: в `dataset.rows` уже только отобранные строки.

## 5. Контракт: `chart.keep`

В действии `answer` поле `chart` расширяется необязательным массивом строк:

```json
{
  "action": "answer",
  "text": "Иванов Иван Иванович — 51730, Босов Александр — 972.",
  "chart": {
    "from": "sql",
    "columns": ["name", "completed"],
    "keep": ["Иванов Иван Иванович", "Босов Александр"]
  }
}
```

| Поле | Правило |
|---|---|
| `keep` | Массив непустых строк. Порядок = порядок столбиков. Дубликаты в `keep`: первая побеждает, повтор игнорируется |
| Пустой массив / нет поля | `keep` не применяем: датасет = последний SQL, как сейчас |
| `from` не `sql` | `keep` в v1 игнорируется (не ошибка). Датасет как сегодня для tool/preload |
| `columns` | Как сейчас: какие поля взять из найденной строки |


Колонка-подпись для матча с `keep` берётся **в том SQL-шаге, где ищем**: первая колонка с типом `text` среди `columns` (если `columns` задан и такие есть), иначе первая `text`-колонка шага. Нет текстовой колонки — этот шаг для `keep` пропускаем.

Поиск строки для каждого имени `k` из `keep`:

1. Идти по `sqlResults` **с конца** (последний успешный SQL первым).
2. В шаге найти первую строку, где значение колонки-подписи **точно равно** `k` (после `Trim`, без смены регистра — кириллица в БД уже в нужном регистре).
3. Собрать из этой строки ячейки по `columns` (или все колонки шага, если `columns` пуст). Числа не пересчитывать. Схема датасета — имена из `columns` либо колонки **первого** успешно найденного шага; в строках из других шагов ячейки кладутся **по имени колонки**. Другое имя меры (`completed` vs `completed_count`) даст null, не «угадывание». Модель, которая склеивает два SQL через `keep`, обязана звать меру одинаково.
4. Если ни в одном шаге нет — имя в датасет не попадает, добавляется в список пропущенных.

Собранный датасет:

- `source`: `sql`
- `rows`: в порядке `keep`, только найденные
- `rowCount`: число найденных (не длина исходного SQL)
- `truncated`: `true`, только если исходный(е) SQL, из которых взяли строки, были усечены **и** мы не смогли найти имя потому что его отрезало; для найденных по полному совпадению — `truncated: false`. Практически: если все `keep` нашлись, `truncated` = false. Если часть не нашлась — не ставим truncated из-за этого, это не усечение, а miss.
- `hint` / `limit`: как сейчас; `limit` режет уже после `keep`

В шаг протокола `answer` рядом с `chart` и `datasetError`:

- `keep` — то, что попросила модель (или null)
- `keepMissing` — имена, которых не нашли (или null / пусто)

`datasetError`:

- Все имена найдены — поля нет / null (как сейчас при успехе)
- Часть не найдена, но хотя бы одна строка есть — график рисуем, `datasetError` = `keep: не найдены: …` (руководитель видит и картинку, и оговорку)
- Не найдено никого — `dataset` = null, `datasetError` объясняет, что `keep` не совпал ни с одной строкой SQL

Модель по-прежнему не может подставить свои числа: нет поля «value» в `keep`.

## 6. Память SQL-шагов

Сейчас в цикле живут `lastSqlCols / lastSqlTypes / lastSqlRows`. Их оставляем (без `keep` поведение не меняется) и параллельно копим список:

```
sqlResults.Add({ cols, types, rows, truncated })
```

только после **успешного** `SqlRun`. Отклонённый валидатором или упавший запрос в список не входит. Неуспешный шаг не затирает предыдущие результаты.

Лимит: все успешные SQL внутри уже существующего потолка шагов агента (10). Отдельный потолок не вводим.

## 7. Промпт

В блок ВИЗУАЛИЗАЦИЯ:

- Если итоговый текст про **подмножество** строк SQL (конкретные ФИО, конкретные подразделения из более широкой выборки) — в `chart.keep` скопировать имена **точно как в столбце результата**.
- Если текст — про весь результат (топ-10, рейтинг) — `keep` не заполнять.
- Не писать в `keep` имена, которых не было ни в одной таблице шагов: график их не выдумает.
- По-прежнему: значения не переписывать; для ответа по SQL обязателен `chart.from=sql`.

## 8. Приёмка

На фикстуре без модели:

| Сценарий | Ожидание |
|---|---|
| SQL1: Босов 972; SQL2: Иванов 51730 + Концева 5061; keep = [Иванов Иван Иванович, Босов Александр] | Две строки, 51730 и 972, Концевой нет |
| Нет keep, последний SQL из 10 строк | 10 строк как сейчас |
| keep с именем, которого нигде нет, плюс один найденный | Одна строка + datasetError со пропущенным именем |
| keep все мимо | dataset null, datasetError |
| from=sql, keep задан, SQL не было | dataset null (как сейчас без lastSqlRows) |

Живой прогон (ручной): вопрос «сравни выполненные задания Иванова и Босова» → в тексте двое, на столбиках двое, числа совпадают с текстом и с таблицами шагов.

## 9. Вне объёма

- `keep` для tool/preload
- Склейка разных колонок подписей (`name` vs `performer`) эвристикой
- Повторный SQL «только эти двое» вместо отбора из уже добытого
- Изменение `charts.js` и чипов видов
