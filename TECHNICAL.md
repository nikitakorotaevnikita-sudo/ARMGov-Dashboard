# Техническая документация

Подробно: какие технические решения и почему приняты, стек и его обоснование, логика сбора
данных из БД, что и в каком объёме уходит в контекст LLM, схема работы сервиса.

Сопутствующие документы: `README.md` (запуск), `PROJECT-OVERVIEW.md` (позиционирование/риски),
`docs/specs/` (проектные спецификации).

## 1. Технические решения и почему

| Решение | Почему так |
|---|---|
| **«Околостоящее» read-only приложение**, а не модуль внутри RX | Штатный деплой в RX был заблокирован (safe mode, рассинхрон `Sungero.Domain.Interfaces`, строгость DTC). Нужна была работающая ценность быстро и независимо от состояния платформы. Решение работает, даже когда виджеты/сервисы RX недоступны. |
| **Прямое чтение PostgreSQL** (`SELECT`), без записи | Самый короткий путь к реальным данным процессов для прототипа. Полностью исключает риск для стенда (ничего не пишем). Компромисс — привязка к физической схеме (см. риски в `PROJECT-OVERVIEW.md`). |
| **Встроенный `HttpListener`**, а не ASP.NET Core | Нулевые внешние зависимости, один самодостаточный exe, минимум кода и поверхности атаки. Для read-only API из ~15 эндпоинтов полноценный веб-фреймворк избыточен. |
| **Ванильный SPA + офлайн SVG/CSS-графика** (без React/Chart.js/CDN) | Закрытый контур: внешние CDN недоступны. Весь фронт — один `index.html`, графики рисуются на SVG/CSS. Нет сборки фронта, нет сетевых зависимостей в браузере. |
| **Вендоренные DLL + резолвер `AssemblyLoadContext`** | Чтобы проект собирался и запускался где угодно: 2 нужные сборки (`Npgsql`, `Microsoft.Extensions.Logging.Abstractions`) лежат в `lib/` и грузятся из папки приложения, без привязки к установке RX. |
| **Конфиг во внешнем `config.json` + env + Бэк-офис** | Секреты вынесены из исходника и истории git; подключения меняются без пересборки (в т.ч. из веб-интерфейса и через переменные окружения для Docker). |
| **Вызовы LLM только на сервере + кэш** | Токен модели не попадает в браузер. Кэш сводки (10 мин) и общего «бандла» данных (2 мин) снижает задержку и нагрузку на модель. |
| **Единый машиночитаемый «бандл» данных** | Один агрегат (`/api/overview` + детали процессов) служит и источником для дашборда, и контекстом для LLM — нет дублирования логики, ИИ «видит» ровно то же, что и экран. |
| **Эвристики маппинга процессов/этапов** | Прагматично для прототипа: типы заданий — по GUID-дискриминаторам, этапы — по справочнику GUID→имя, НПА — по тексту темы. Достаточно для демо; для продукта заменяется на метаданные RX. |
| **Self-contained / Docker / `run.bat`** | Разные способы развёртывания: переносимый бандл без установки .NET, контейнер, простой запуск на Windows. |

## 2. Стек технологий и обоснование

| Слой | Технология | Почему |
|---|---|---|
| Платформа | **.NET 10** (C#) | Совместимость со сборками RX (та же `Npgsql`), производительность, единый бинарь. |
| HTTP | **`System.Net.HttpListener`** | Встроен в рантайм, без зависимостей; достаточно для статики + JSON-API. |
| СУБД-драйвер | **Npgsql** | Стандартный драйвер PostgreSQL; та же версия, что в дистрибутиве RX (вендорим её). |
| Сериализация | **`System.Text.Json`** | Встроенная, быстрая, без зависимостей. |
| Frontend | **Vanilla JS + HTML + CSS**, графика на **SVG/CSS** | Офлайн-контур, нулевая сборка, переносимость; дизайн-система **Platform.ОГВ/Directum** (`tokens.css`). |
| ИИ | **OpenAI-совместимый эндпоинт (vLLM «Ario»)**, модель **Qwen/Qwen3.6-35B-A3B** | Уже доступен в контуре; протокол OpenAI прост (`/v1/chat/completions`); окно контекста 131k токенов с запасом. |
| Доставка | **self-contained publish (win-x64)**, **Docker**, `run.bat` | Запуск без установленного .NET / в контейнере / простым кликом. |

## 3. Логика сбора данных из БД

### 3.1 Используемые таблицы (только чтение)

- **`sungero_wf_task`** — экземпляр процесса (поручение/обращение/НПА). Ключевое: `discriminator`
  (тип процесса), `subject`, `status`, `created`.
- **`sungero_wf_assignment`** — задание/этап внутри задачи. Ключевое: `task`, `discriminator`
  (тип этапа), `performer`, `author`, `created`, `deadline`, `completed`, `status`.
- **`sungero_core_recipient`** — сотрудники и подразделения (single-table). Связь сотрудник→
  подразделение через `department_company_sungero` → запись-подразделение (имя = `name`).
- **`sungero_wf_workflowhistory`** — события (`operation`, `historydate`, `entityid`, `user`);
  используется операция **`MarkRead`** (когда задание открыли) для метрик времени решения.

> Таблицы `sungero_content_edocversion` и `dirrx_genai_*` исследовались на этапе анализа, но в
> рантайме **не используются** (объём документа и креды LLM в итоговую логику не вошли — креды
> задаются в конфиге).

### 3.2 Определение процессов и этапов

- Процесс = условие отбора задач: **Поручения** `discriminator='c290b098-…'`, **Обращения граждан**
  `discriminator='4ef03457-…'`, **НПА** — эвристика по теме (`subject ilike '%НПА%' / %регламент% / …`).
- Этап = `assignment.discriminator`, маппится по справочнику GUID→имя
  (`Исполнение`, `Контроль / приёмка`, `Доработка`, `Прочее`); неизвестные → «Этап N».

### 3.3 Как считаются метрики (SQL «на лету»)

- **Сквозная пропускная способность** = `в срок / (в срок + просрочено)` на уровне заданий, где
  «в срок» = `Completed && completed<=deadline`, «просрочено» = `Completed&&completed>deadline`
  **или** `InProcess&&deadline<now()`.
- **Узкое горлышко** = по каждому (процесс, этап) медиана возраста активных заданий
  `percentile_cont(0.5)` от `now()-created` для `InProcess` + размер очереди; ранжирование по
  убыванию, #1 — главное.
- **Долгострои** = `InProcess && deadline < now() - 3 дня`.
- **Здоровье процесса** = `1 − просроченные_активные / активные` (× 100).
- **Время цикла по этапам** = `percentile_cont(0.5/0.95)` от `completed−created` по завершённым
  заданиям этапа (P50/P95).
- **Распределение длительности маршрута** = `max(completed|now)−min(created)` по задаче,
  разложение по корзинам дней (0–7/8–30/31–90/91–180/180+).
- **Тренд дисциплины** = помесячно (по месяцу `deadline`) `count filter` для «в срок»/«просрочено».
- **Прогноз срыва срока** = активные задания по близости к сроку: просрочено / ≤3 дн (критично)
  / ≤7 дн (под риском) / запас.
- **Воронка** = по этапам `total / done(Completed) / active(InProcess) / overdue`.
- **Карта возвратов («битва правок»)** = `count` заданий типа `Доработка` (disc `ef79164b-…`)
  с группировкой по `author` (кто инициировал возврат).
- **Время и качество решения** = медиана `completed−created`; плюс «открыл→решил» = `completed −
  min(historydate)` по событию `MarkRead` (через подзапрос first_read); «пустое согласование» =
  доля решений быстрее 5 минут после открытия.
- **Загрузка исполнителей** = по `performer`: активные / просроченные / завершённые / в срок /
  среднее удержание; «перегруз» если активных > 1.5 × среднего по команде.
- **Распределение по подразделениям** = задача относится к подразделению **последнего**
  исполнителя (`distinct on (task) … order by created desc`), затем агрегация по подразделению.
- **Просроченные (гистограмма)** = активные просроченные, корзины по дням просрочки `now−deadline`.
- **Поток-эффективность** = по завершённым заданиям с событием `MarkRead`: `работа = Σ(completed −
  first_read)`, `всего = Σ(completed − created)`; effPct = работа/всего; ожидание = всего − работа.
- **Скорость реакции (pickup)** = `first_read − created` (сколько лежит до взятия в работу),
  среднее/медиана + по этапам. (Разрыв «между этапами» не считаем — RX создаёт следующий этап мгновенно, gap≈0.)
- **С первого раза (FTR)** = доля задач, у которых `not exists` задания типа `Доработка`.
- **Петли** = доля задач, где этап (discriminator) встречается > 1 раза; + частые переходы (`lag()`).
- **Приток/отток** = помесячно: создано (`t.created`) vs завершено (`max(a.completed)`).
- **Дельта пропускной способности** = последний месяц vs предыдущий из помесячного тренда (п.п.).
- **Разрезы** = по исполнителю (`/workload`), ведомству (`/departments`), виду рассмотрения
  (`/by-kind` по `processkind`).
- **Карточка задания** = шапка + хронология этапов; **исполнитель** = помесячная дисциплина +
  его активные задания (со ссылкой в RX).
- **Экспорт CSV** (`/api/export`) = просроченные / загрузка / подразделения; `;`-разделитель + BOM (Excel).

### 3.4 Приёмы и безопасность запросов

- Используются `percentile_cont(... ) within group`, `count(*) filter (where …)`, `distinct on`,
  CTE (`with`).
- **Инъекций нет:** в SQL подставляются только константы (GUID-дискриминаторы, выбираемые
  серверным справочником процессов), а пользовательские параметры (`id`, `dept`) приводятся к
  `long` или передаются параметром (`@d`). Произвольные строки от клиента в SQL не попадают.
- Все соединения — отдельные, короткоживущие, `Command Timeout=120`, `SSL Mode=Prefer`.

## 4. Данные в контексте LLM

### 4.1 Что собирается (бандл)

`BuildAiBundle()` формирует единый машиночитаемый агрегат:
```
{
  generatedAt,
  overview,                      // = /api/overview (регион + сводка по процессам)
  detail: {
    poruchenia: { process, workload },   // = /api/process + /api/process/workload
    appeals:    { process, workload },
    npa:        { process, workload }
  }
}
```
То есть в модель уходят: региональные индикаторы, и по каждому из 3 процессов — KPI, этапы
(P50/P95), воронка, возвраты и их авторы, время/качество решения, топы исполнителей, варианты
маршрута, загрузка по людям. Это ровно те же данные, что показывает дашборд.

### 4.2 Объём (замерено на текущем стенде)

| Часть | Размер |
|---|---|
| overview | ~4.3 КБ |
| Поручения (process + workload) | ~8.1 КБ |
| Обращения (process + workload) | ~4.9 КБ |
| НПА (process + workload) | ~4.8 КБ |
| **Итого бандл** | **~22 КБ JSON** |

Грубая оценка — **≈ 8–9 тыс. токенов** (кириллический JSON), при окне модели **131 072 токена**
это **~7 %** контекста. Запас многократный: данные влезают целиком, без усечения/RAG.

### 4.3 Как используется

- **Сводка** (`GET /api/ai/summary`): `system` (роль «старший аналитик», три раздела) + `user`
  (бандл JSON). `max_tokens=1500`, `temp=0.3`. Кэш 10 мин (кнопка «обновить» — принудительно).
  С параметром `?key=<процесс>` — сводка по конкретному процессу (контекст = его `process+workload`),
  кэш по ключу. Кнопка «✦ Сводка ИИ» на странице процесса.
- **Разбор блока** (`POST /api/ai/explain`): по клику на ⓘ — короткое пояснение метрики на
  текущих данных процесса.
- **Чат** (`POST /api/ai/chat`): `system` (отвечать только по данным, не выдумывать) + бандл +
  история диалога из браузера. `max_tokens=1000`, `temp=0.4`. Сервер без состояния — историю
  хранит клиент, контекст данных подставляется на каждый запрос.
- **Кэш бандла** — 2 минуты (чтобы чат не пересчитывал агрегаты из БД на каждое сообщение).
- **Грунтинг:** модель инструктируется опираться только на переданный JSON; на практике сводка
  и ответы цитируют реальные цифры (например, «119 возвратов», «медиана 295 дней»).

### 4.4 Приватность (важно для госконтура)

В бандл попадают **имена сотрудников** (исполнители, авторы возвратов) — это персональные данные,
которые уходят на внешний LLM-эндпоинт. Для продуктива требуется: размещение модели в контуре,
обезличивание или согласие/правовое основание. Сейчас — на ответственности оператора стенда.

## 5. Схема работы сервиса

### 5.1 Компоненты и потоки

```
                            ┌─────────────────────────────────────────────┐
                            │  Браузер (SPA, один index.html)              │
                            │  • Обзор региона / Процессы / Бэк-офис        │
                            │  • ИИ-сводка + чат  • графики SVG/CSS         │
                            └───────────────┬─────────────────────────────┘
                                            │ HTTP (localhost:5080), JSON
                                            ▼
        ┌────────────────────────────────────────────────────────────────────┐
        │  armgov-standalone (.NET 10, HttpListener)                           │
        │                                                                      │
        │  Статика: index.html, tokens.css, logo                              │
        │  API данных:  /api/overview · /api/process[/stuck|/workload|         │
        │               /departments|/dept-tasks|/by-kind] · /api/task ·        │
        │               /api/performer · /api/export (CSV)                      │
        │  ИИ:          /api/ai/summary[?key=] · /api/ai/chat · /api/ai/explain  │
        │  Конфиг:      /api/config (GET/POST) · /api/config/test               │
        │  (профили, период ?period=, дельты, пороги — поверх этих эндпоинтов)   │
        │                                                                      │
        │  config.json (host/пароль БД, url/токен модели) ← env-override        │
        └───────┬───────────────────────────────────────────────┬────────────┘
                │ Npgsql, только SELECT                           │ HTTPS, server-side
                ▼                                                 ▼
   ┌────────────────────────────┐                  ┌────────────────────────────────┐
   │  PostgreSQL (БД Directum RX)│                  │  LLM «Ario» (vLLM, OpenAI API) │
   │  sungero_wf_task /          │                  │  Qwen/Qwen3.6-35B-A3B           │
   │  assignment / recipient /   │                  │  /v1/chat/completions          │
   │  workflowhistory            │                  └────────────────────────────────┘
   └────────────────────────────┘
```

### 5.2 Жизненный цикл запроса

1. **Старт:** `LoadConfig()` читает `config.json` (+ env-переопределения) → `HttpListener`
   слушает `Prefix` (по умолчанию `http://localhost:5080/`).
2. **Метрики:** браузер запрашивает `/api/*` → обработчик строит SQL, открывает короткое
   соединение Npgsql, агрегирует, отдаёт JSON. Данные считаются «на лету».
3. **ИИ-сводка:** `/api/ai/summary` → (кэш 10 мин) → `BuildAiBundle()` (кэш 2 мин) → промпт →
   POST в Ario → текст из 3 разделов.
4. **ИИ-чат:** `/api/ai/chat` (POST, история от клиента) → бандл как контекст → Ario → ответ.
5. **Бэк-офис:** `/api/config` GET (секреты маскируются) / POST (сохранение в `config.json`,
   сброс кэшей; смена БД/модели — сразу, смена адреса прослушивания — после перезапуска);
   `/api/config/test` — пинг БД и модели.

### 5.3 Последовательность ИИ-сводки

```
Браузер → GET /api/ai/summary
   └─ есть свежий кэш (<10 мин)? → да → вернуть кэш
                                  → нет ↓
        BuildAiBundle (кэш бандла <2 мин, иначе ~6 SQL-агрегатов из БД)
        → messages = [system: «аналитик…», user: bundle(~22КБ)]
        → POST Ario /v1/chat/completions (max_tokens=1500)
        → текст (3 раздела) → кэшировать → вернуть
```
