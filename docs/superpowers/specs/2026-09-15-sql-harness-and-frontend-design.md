# ИИ-харнесс запросов к БД и выравнивание фронтенда — дизайн

**Дата:** 2026-09-15
**Проект:** ARMGov-Dashboard (прототип проверки гипотез)
**Автор постановки:** Никита Коротаев
**Эталон:** `presale-dashboard` (`src/code_agent.py`, `src/agent_sandbox.py`, `static/tokens.css`, `static/style.css`)

## 1. Задача

Две независимые части в одном прототипе.

**Харнесс.** Сегодня ИИ-чат работает по «подходу A»: весь JSON метрик кладётся в системный промпт, модель только интерпретирует готовые числа. Это надёжно, но отвечает лишь на то, что уже посчитано дашбордом, и стоит 35 секунд на вопрос (замер 15.09.2026 — почти вся задержка идёт на обработку промпта). Нужен режим, в котором модель сама достаёт данные из базы RX: произвольные срезы, кросс-расчёты, вопросы, которых нет в сводке. Числа в ответе должны браться из фактически выполненного запроса, а не из «памяти» модели.

**Фронтенд.** Прототип и presale-dashboard должны выглядеть одним продуктом. Токены уже общие — `tokens.css` в обоих проектах побайтово одинаков, `data-theme="state-1"` выставлен, хардкод-цветов осталось 12. Расходится слой компонентов и типографика.

## 2. Решения по объёму (согласованы)

| Развилка | Решение |
|---|---|
| Что исполняет харнесс | Сырой `SELECT` к базе RX |
| Граница безопасности | Валидатор в коде + read-only транзакция (отдельную учётку БД не заводим) |
| Схема для модели | Ручной словарь ядра (10–15 таблиц) + действие «справка по таблице» |
| Архитектура цикла | Многошаговый агент (вариант B), до 6 шагов |
| Место в UI | Тумблер в существующем дровере «Спросить ИИ» |
| Показ хода | Один JSON с протоколом шагов; в чате — раскрывающийся блок размышлений |
| Шрифт Inter | Вшить локально, без Google Fonts |
| Глубина выравнивания | Компоненты и типографика; экраны и навигация не трогаются |

Замер, на котором основан выбор B: короткий промпт (150 токенов вход, 49 выход) — **1,5 с** на вызов. Цикл из 3–4 шагов укладывается в 8–12 секунд вместе с выполнением SQL. Отсюда правило: **в промпт агента сводка метрик не попадает никогда** — именно она делает нынешний чат 35-секундным.

## 3. Ограничения

- .NET 10, `HttpListener`, Npgsql, `System.Text.Json`; вся логика в `Program.cs`, фронтенд в `index.html` — архитектуру прототипа не меняем.
- **Только `SELECT`** — нерушимое правило проекта (`CLAUDE.md` §1). Харнесс не имеет права его ослабить.
- Секретов в коде нет; токен LLM и пароль БД — только в `config.json` рядом с exe.
- Уведомления (`*Notice`/`*Notification`) исключаются из статистики — правило должно попасть в промпт агента.
- Общение с пользователем и весь UI — по-русски.

## 4. Компоненты

```
Program.cs
├── SqlGuard.Check(sql)   → {ok, reason, effective}   — валидатор, без побочных эффектов
├── SqlGuard.Run(sql)     → {cols, rows, ms}          — исполнитель в read-only транзакции
├── SqlAgent.Ask(messages)→ {reply, steps, elapsedMs} — цикл агента
├── SchemaDict            — словарь ядра + справка по таблице из information_schema
└── эндпоинты: POST /api/ai/sql, GET /api/ai/sql/check

index.html
├── тумблер «Глубокий анализ (SQL)» в дровере чата
└── блок «Размышления · N шагов · T с» — раскрывается в ленту шагов

style.css (новый)  — стили, вынесенные из index.html, + компоненты по presale
static/inter-*.woff2 — шрифт локально
```

Каждая единица — одна ответственность и проверяется отдельно: валидатор через `/api/ai/sql/check` без похода в базу, исполнитель — на заведомо корректном запросе, цикл — на живом вопросе.

## 5. Протокол агента

Системный промпт: роль, словарь ядра схемы, правила расчёта проекта, описание протокола. Модель на каждом шаге возвращает **один JSON-объект**:

```json
{"thought": "…", "action": "schema", "table": "sungero_wf_assignment"}
{"thought": "…", "action": "sql", "query": "SELECT …", "purpose": "…"}
{"thought": "…", "action": "answer", "text": "…"}
```

`thought` обязателен — он же содержимое раскрывающегося блока в чате.

**Почему не штатный tool-calling OpenAI.** У провайдера Ario/vLLM поддержка `tools` не гарантирована, а конфиг умеет переключаться на GigaChat. JSON-протокол одинаково работает на обеих моделях и не зависит от смены провайдера.

**Правила цикла:**

- максимум **6 шагов**, общий бюджет **60 секунд**;
- результат действия возвращается модели коротким сообщением: таблица ≤ 50 строк, ячейки обрезаются;
- при исчерпании бюджета последний вызов просит ответить по уже собранным данным — не обрыв с ошибкой, а ответ с пометкой `truncated: true`;
- если модель вернула не-JSON или неизвестное действие, ей возвращается текст ошибки разбора, и это стоит шага;
- на `answer` цикл завершается.

**Словарь ядра** — ровно те таблицы, которые прототип уже использует (проверено по `Program.cs` 15.09.2026): `sungero_wf_task`, `sungero_wf_assignment`, `sungero_core_recipient`, `sungero_wf_workflowhistory`, `sungero_system_entitytype`, `sungero_content_edoc`, `sungero_recman_taicoassignees`, `sungero_recman_taiparts`, `sungero_recman_taipartscoasgs`, `sungero_wf_processkind`, `sungero_company_jobtitle`, `sungero_parties_counterparty`. Для каждой — назначение, ключевые колонки, связи. Плюс правила: просрочка = `status='InProcess' and deadline < now()`, `Aborted` не считается, уведомления исключаются, дедупликация по `maintask`.

**Справка по таблице** (`action: schema`) берётся из `information_schema.columns` плюс два примера значений на колонку. Закрывает слепоту ручного словаря за пределами ядра, не раздувая промпт.

## 6. Гардрейлы

**Валидатор `SqlGuard.Check`** — по тексту, до выполнения:

1. вырезаются комментарии (`--`, `/* */`), и дальше **исполняется именно очищенный текст** — иначе проверялось бы одно, а в базу уходило другое;
2. ровно один оператор: точка с запятой допускается только хвостовая;
3. текст начинается с `select` или `with`;
4. деней-лист по границам слов: `insert, update, delete, drop, alter, create, truncate, grant, revoke, copy, vacuum, call, do, set, reset, begin, commit, rollback, dblink, pg_read_file, pg_ls_dir, lo_import, lo_export, pg_sleep`;
5. если `limit` отсутствует — запрос оборачивается: `select * from (<запрос>) t limit 200`.

**Исполнитель `SqlGuard.Run`** — отдельное соединение:

```sql
BEGIN; SET TRANSACTION READ ONLY; SET LOCAL statement_timeout = '10s';
<запрос>
ROLLBACK;
```

Read-only транзакция — второй рубеж: даже пропущенная валидатором запись будет отклонена самим PostgreSQL. `statement_timeout` не даёт повесить стенд тяжёлым джойном. Капы на выдачу: 200 строк, 60 колонок, 200 символов на ячейку.

**Остаточный риск.** Исполнимый, но логически неверный SQL даст точное-и-неправильное число. Смягчение: SQL виден пользователю, режим opt-in, надёжный чат по сводке остаётся дефолтом. Отдельная read-only учётка БД остаётся в роадмапе как настоящая граница — сейчас дашборд ходит учёткой с широкими правами (`CLAUDE.md`, «Известные хрупкости»).

## 7. Контракт ответа

`POST /api/ai/sql`, тело `{messages:[{role,content}]}`:

```json
{ "reply": "…",
  "steps": [
    {"n":1, "action":"schema", "thought":"…", "table":"sungero_wf_assignment", "ms":1480},
    {"n":2, "action":"sql", "thought":"…", "sql":"SELECT …", "purpose":"…",
     "rows":12, "ms":1610, "cols":["подразделение","просрочено"],
     "preview":[["ДИТ",412],["ДФ",311]]},
    {"n":3, "action":"answer", "thought":"…", "ms":1520}
  ],
  "elapsedMs": 8390, "truncated": false }
```

Ошибка LLM или БД отдаётся полем `error` с русским текстом — как в остальных ИИ-эндпоинтах прототипа, без 500.

`GET /api/ai/sql/check?q=…` → `{ok, reason, effective}`. Только проверка, в базу не ходит. Существует ради тестируемости валидатора.

## 8. Фронтенд

1. **Inter локально.** `static/inter-400/600/700.woff2` + `@font-face`. Токен `--font` уже ссылается на Inter — сейчас шрифт просто не приезжает, и прототип рисуется в Segoe UI.
2. **Стили из `index.html` — в `style.css`**, подключается после `tokens.css`; файл добавляется в копирование статики в `.csproj`.
3. **Компоненты по `presale-dashboard/static/style.css`**: `.btn`/`.btn-ghost`/`.btn-sm`, поля ввода с фокус-кольцом `0 0 0 3px var(--accent-soft)`, вкладки `.tab`, сегментные переключатели `.seg`, KPI-карточка с верхней акцентной гранью, таблицы с `surface-2`-шапкой и `tabular-nums`, чат-бабблы и markdown-правила. Оставшиеся 12 хардкод-цветов уходят в токены.

Экраны, навигация, сайдбар не трогаются.

## 9. Тестирование

- **Валидатор** — новые кейсы в `tests/smoke.py` через `/api/ai/sql/check`: `drop table`, два оператора через `;`, маскировка комментарием, запрос без `limit` (ожидается обёртка), корректный запрос.
- **Исполнитель** — smoke-проверка, что `/api/ai/sql/check` не ходит в базу, и один живой запрос через `/api/ai/sql`.
- **Цикл** — живой прогон реального вопроса: ответ содержит непустой `reply`, `steps` с хотя бы одним `action:"sql"`, `elapsedMs` в пределах бюджета.
- **Фронтенд** — полный прогон `tests/smoke.py` (53 проверки) плюс просмотр всех пяти экранов в браузере до и после.

Ожидаемый результат smoke после работ: `PASS=58+ FAIL=0`.

## 10. Порядок работ

Сначала фронтенд — он изолирован и легко откатывается, после него smoke должен остаться зелёным. Затем харнесс: валидатор с тестами → исполнитель → словарь схемы → цикл агента → эндпоинты → UI чата.

## 11. Вне объёма (YAGNI)

- Стриминг ответа (переделка транспорта в `HttpListener`) — цикл укладывается в 8–12 секунд, хватает спиннера.
- Отдельная read-only учётка БД — в роадмап, требует действий на стенде.
- Память диалога между сессиями, история запросов.
- Графики по результату запроса.
- Перестройка каркаса экрана (верхняя навигация вместо сайдбара).
