# CLAUDE.md — АРМ руководителя (ARMGov-Dashboard)

Язык общения — русский.

Read-only веб-дашборд над БД Directum RX для первого лица: состояние процессов за 10 секунд с проваливанием до конкретного поручения. .NET 10 + `HttpListener`, без ASP.NET. Бэкенд — `Program.cs` (~225 КБ, включает ИИ-харнесс — см. ниже); фронтенд — `index.html` (SPA на ванильном JS, ~225 КБ) + вынесенные `style.css`/`tokens.css`, локальный шрифт Inter (шесть `.woff2`). Статус — рабочий прототип на одном стенде.

---

## Нерушимые правила

1. **Только `SELECT`.** Приложение никогда не пишет в БД RX. Правка, добавляющая `INSERT`/`UPDATE`/`DELETE` или DDL — ошибка, а не фича.
2. **Секретов в коде нет.** Пароль БД и токен LLM живут только в `config.json` рядом с exe (в `.gitignore`) или в env `ARMGOV_DB_PASSWORD` / `ARMGOV_LLM_TOKEN`. В браузер не возвращаются — маскируются. **Этот файл в git — не писать сюда креды.**
3. **Метрики должны сходиться друг с другом.** `FTR% + петли% ≈ 100%`; воронка сходится к итогу этапа (`завершено + в работе + просрочено + прервано = всего`); просрочка в KPI совпадает с просрочкой в блоке риска; все временные границы считаются в SQL через `now()`. Заказчик проверяет цифры одну о другую — ломать согласованность нельзя даже ради «более правильной» отдельной метрики.
4. **Уведомления исключаются из статистики.** Типы `*Notice`/`*Notification` подгружаются из `sungero_system_entitytype` при старте и вычитаются из всех метрик. Новая метрика обязана это учитывать.

## Окружение и сборка

Проверено 28.07.2026 на этой машине.

**`dotnet` не в PATH у новой сессии PowerShell**, хотя SDK 10.0.302 установлен в `C:\Program Files\dotnet`. Перед сборкой:

```bash
$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')
```

Сборка и запуск:

```bash
dotnet build -c Release && bin\Release\net10.0\armgov-standalone.exe
```

- **Статику копирует сборка** (`armgov-standalone.csproj`: `index.html`, `tokens.css`, `style.css`, `charts.js`, `logo-directum.svg`, шесть файлов шрифта Inter `.woff2`, `config.json` при наличии). Указание в README копировать `index.html` вручную устарело.
- `index.html`, `style.css`, `charts.js` читаются сервером **на каждый запрос** — правка фронта не требует ни пересборки, ни перезапуска, достаточно обновить страницу. Но файл должен быть обновлён в `bin\Release\net10.0\`, а не только в корне.
  **`charts.js` — не только про графики:** `esc()` переехала туда и вызывается из `renderNav` при старте страницы. Отсутствующий или устаревший `charts.js` в выходной папке ломает весь SPA целиком, а не только экран «Аналитика по запросу» — раньше `index.html` был самодостаточен.
- Порт 5080, слушает `http://localhost:5080/`.
- Портативный бандл: `dotnet publish -c Release -r win-x64 --self-contained true -o dist`.

## Проверка после изменений

```bash
python tests/smoke.py http://localhost:5080
python tests/analysis_smoke.py http://localhost:5080
node tests/charts.test.js
node tests/analysis.test.js
dotnet run --project tools/harness-tests -c Release -- all
dotnet restore --locked-mode
dotnet publish -c Release -r win-x64 --self-contained true --no-restore -o .\artifacts\workflow-publish
```

`smoke.py` — регрессия дашборда и legacy SQL-харнесса (scope policy намеренно отклоняет `pg_settings`/`information_schema` вне каталога). `analysis_smoke.py` — wire + semantic cases для `POST /api/ai/analysis` (offline без `--live`; live отдельно). Контракт: [docs/technical/analytics-harness-v2.md](docs/technical/analytics-harness-v2.md).

`charts.test.js` / `analysis.test.js` — чистые функции визуализации и рендера verified report.

Live gate выполняется отдельно после явного переключения `Analytics.Engine` и перезапуска
Release-сервера: для `legacy`, затем для `workflow` запустить
`python tests/analysis_smoke.py http://localhost:5080 --live --engine <engine> --repetitions 3`.
Каждый прогон обязан выполнить все 10 кейсов трижды. Артефакты в `artifacts/analytics-eval/`
содержат только case/status/timing, безопасные поля шагов, `resultId` и effective SQL; строки,
headers, provider payload и секреты туда не пишутся. Exit `1` — semantic failure, exit `2` —
только provider/RX unavailable.

**После правки `charts.js` в выходной папке (`bin\Release\net10.0\charts.js`) проверяй не только новый экран «Аналитика по запросу», а хотя бы один из пяти старых** — `esc()` теперь живёт там же и нужна `renderNav` при самом первом рендере страницы, так что устаревший файл ломает весь SPA, а не только новый вид.

**Smoke не покрывает** эндпоинты: `/api/my/tasks`, `/api/appeals/topics`, `/api/appeals/systemic`, `/api/process/kind-tasks`, `/api/performer`. Их проверять руками. При добавлении нового эндпоинта — дописывать в smoke.
`/api/leaders` и `/api/leader/tasks` покрыты частично: разрез `bu`, поле `coOverdue`, контракт «`coOverdue>0` ⇒ `risk`» и тип `co.total`. Не покрыты разрешение имён организаций и дедупликация участников в `co.items`.

Ad-hoc SQL к стенду: `dotnet run --project tools/dbq -- "<SQL>"` (берёт креды из `config.json`, см. `tools/dbq/QUERIES.md`).

## Известные хрупкости

- **Идентификация процессов завязана на конкретный стенд.** Поручения и обращения опознаются по GUID-дискриминаторам, НПА — эвристикой `ilike` по тексту темы, этапы маршрута мапятся по фиксированным GUID. На другом стенде или после обновления платформы аналитика поедет. Это главный архитектурный риск, он же — основание для перехода на OData/метаданные RX в будущем.
- **Молчаливый `catch` при старте** — [Program.cs:305](Program.cs:305). Недоступная БД по логу неотличима от рабочей. Различать по строке в логе: `Notice types excluded from stats: 4` — это захардкоженный фолбэк, запрос к БД упал; `54` — реальный запрос прошёл.
- Метрики считаются на лету при каждом запросе (кэш ответов TTL 60с), индексной оптимизации нет.
- Аутентификации пользователя в дашборде нет; используется учётка БД с широкими правами. Для прода нужна отдельная read-only учётка.
- Автотестов кроме smoke нет; проект ведёт один разработчик.
- **ИИ-харнесс исполняет сгенерированный моделью SQL.** Два рубежа: валидатор `SqlCheck`
  (один оператор, только SELECT/WITH, два списка запретов — ключевые слова по границам слова
  и семейства функций по префиксу, разбор строковых литералов, безусловная обёртка `limit 201`)
  и исполнение `SqlRun` в read-only транзакции со `statement_timeout` 10 секунд и лимитами
  200 строк / 60 колонок / 200 символов на ячейку. Остаточный риск — запрос может пройти оба
  рубежа, будучи исполнимым, но логически неверным: он даст точное на вид и при этом
  неправильное число. Смягчение: ключевые метрики агент берёт готовыми инструментами (см.
  «Где что документировано» → спека), а не считает SQL сам; исполненный запрос виден
  пользователю в раскрывающемся блоке «Размышления»; режим включается тумблером и по
  умолчанию выключен.
- **Настоящего второго рубежа для SQL-харнесса пока нет.** Между обходом валидатора и записью
  в БД сейчас стоит только read-only транзакция, которую выставляет наш же код (`set
  transaction read only`) — отдельной учётки БД, физически неспособной писать, не заведено;
  дашборд и харнесс ходят в Polud одной и той же полнопривилегированной учёткой. Завести
  read-only роль в PostgreSQL и переключить на неё `config.json` — обязательное условие перед
  показом прототипа вне своего контура, не просто «хорошо бы».
- **Режим «Глубокий анализ (SQL)» работает только при локальном вызове.** Эндпоинты
  `/api/ai/sql`, `/api/ai/sql/check`, `/api/ai/sql/run` закрыты проверкой `IsLocalCall`
  (физический адрес запроса + заголовок `Host` — оба обязаны быть loopback). Если прототип
  выставят в локальную сеть для показа коллегам, у удалённых зрителей тумблер не даст ответа —
  это осознанное безопасное поведение, а не баг, чинить не нужно.
- **По той же причине страница «📈 Аналитика по запросу» недоступна при сетевом показе.** Она
  обращается к `/api/ai/analysis` (управляемый workflow с verified report), а не к публичному
  эндпоинту — значит, тот же
  `IsLocalCall`-периметр закрывает и её у удалённых зрителей. Отдельного тумблера тут нет: страница
  либо работает целиком, либо у неё нет доступных данных вовсе.

## Работа с заметками Obsidian

- **Читать в UTF-8.** `Get-Content` в PowerShell 5.1 без `-Encoding utf8` превращает кириллицу в мусор и приводит к ложным выводам — так однажды получился фантомный список «битых» ссылок. Надёжнее `[IO.File]::ReadAllText()` или MCP-сервер Obsidian.
- Подключён MCP `obsidian` (`http://127.0.0.1:27123/mcp/`, Local REST API). Даёт индекс ссылок (`links`/`backlinks`/`unresolvedLinks`), JsonLogic-поиск по метаданным, точечное чтение и правку по заголовкам. HTTPS-порт 27124 не использовать — самоподписанный сертификат, Node его отклоняет.
- **Формат ссылок:** `[[полное-имя-файла|короткий текст]]`. Короткие `[[TICKET-NN]]` не резолвятся, потому что статус-эмодзи входит в имя файла; алиасы во frontmatter это **не** лечат — проверено 28.07.2026, индекс Obsidian их при разрешении ссылок не учитывает.
- Классы документов: артефакт события — `YYYY-MM-DD_...`, живой документ — без даты в имени.
