# «Личный контроль» в блоке «Мои задания» — дизайн

**Дата:** 2026-07-13
**Контур:** web-прототип ARMGov (`index.html` + `Program.cs`). После подтверждения на демо — перенос в RX-native по пайплайну (см. правило prototype-to-rx-workflow).

## Проблема

Блок «Мои задания» на стартовой странице «Обзор для руководителя» сейчас **автоматически** показывает топ-3 активных задания демо-руководителя (`DemoUserId=53`, «Босов Александр»), отсортированных по срочности ([Program.cs:462-495](../../../Program.cs#L462-L495), [index.html:461-477](../../../index.html#L461-L477)).

Руководитель хочет **сам выбирать** входящие задания, которые требуют его личного контроля, чтобы они всегда были под рукой на дашборде — а не полагаться только на авто-сортировку по сроку.

## Решения (по итогам брейншторминга)

1. **Область выбора:** только собственный инбокс — активные задания, где `performer=DemoUserId`. Не расширяем на чужие объекты/документы.
2. **Компоновка:** один блок «Мои задания». Закреплённые вручную задания — сверху с маркером 📌, оставшиеся места добиваются авто-топом по срочности.
3. **Выбор:** кнопка в шапке блока открывает модалку со списком всех активных заданий; у каждого — переключатель 📌.
4. **Персистентность:** `localStorage`, ключ привязан к пользователю. Прототип read-only к продуктивной БД; localStorage уже используется для раскладки блоков ([index.html:655](../../../index.html#L655)).

## Архитектура

Вся логика пина и слияния — **на клиенте**. Бэкенд не знает про «избранное», лишь отдаёт полный список активных заданий. Обосновение: продуктивная БД read-only («без битья по БД»), а localStorage — уже штатный механизм пер-юзер UI-состояния в прототипе.

Отклонённые альтернативы: хранение пинов в БД (нельзя — read-only); серверный cookie/файл-стор (лишняя машинерия ради демо).

### Бэкенд — `Program.cs`, `BuildMyTasks()`

Endpoint `/api/my/tasks` расширяется:

- Возвращает `all` — **все активные задания** пользователя (`status='InProcess'`, `performer=DemoUserId`, с исключением уведомлений `NoticeList`), кап **50**, отсортированные по той же срочности (просрочено → скоро → без срока → по дедлайну).
- Каждый элемент — те же поля, что сейчас в `top`: `{id, subject, stage, process, deadline, overdue, dueKind, dueLabel, rxLink}`. `id` = `a.id` (идентификатор задания-ассайнмента) — ключ для пина.
- Счётчики `active`/`overdue` — без изменений.
- Поле `top` из ответа **удаляется** — клиент теперь сам режет `all`. Старый рендер `top` в `renderMyTasks` заменяется логикой пинов.

Один запрос кормит и модалку (весь список), и блок (клиент выбирает подмножество).

### Фронтенд — `index.html`

**Хранилище пинов:**
- Ключ: `armgov.mycontrol.<DemoUserId>` → JSON-массив id закреплённых заданий (в порядке добавления).
- Функции-хелперы по образцу `loadLayout`/`saveLayout` ([index.html:655-656](../../../index.html#L655-L656)): `loadPins()`, `savePins(arr)`, `togglePin(id)`.

**Блок «Мои задания» (`renderMyTasks`):**
- Читает `all` из ответа и пины из localStorage.
- Список к показу = закреплённые (в порядке пина, каждое с бейджем 📌) + авто-добор оставшихся по срочности, исключая уже закреплённые.
- Кап показа: закреплённых максимум **5**; если пинов меньше 3 — добиваем авто-топом до **3** (текущее поведение). Итоговый максимум карточек — 5.
- **Самозаживление:** id из пинов, которого нет в `all` (задание завершилось/пропало из инбокса), молча отбрасывается при рендере и вычищается из localStorage.
- В шапке блока — кнопка **«⚙ Настроить контроль»**, открывающая модалку.
- Пустой инбокс — прежнее «нет активных заданий».

**Модалка выбора (`#mycontrolModal`):**
- Паттерн как у существующих модалок: `<div class="overlay hidden" onclick="if(event.target===this)closeMyControl()"><div class="modalbox">…`.
- Заголовок + список всех активных заданий из `all`: тема, этап/процесс, срок (с цветом по `dueKind`), справа — кнопка-переключатель 📌 (активный/неактивный вид).
- Клик по 📌: `togglePin(id)` → сохранение в localStorage → живая перерисовка и блока, и списка в модалке.
- Открытие: `openMyControl()`, закрытие: `closeMyControl()` (снятие/добавление класса `hidden`), по образцу `openAi`/`closeAi`.

## Данные и потоки

```
/api/my/tasks (BuildMyTasks)
   → { user, active, overdue, all:[{id,subject,stage,process,deadline,overdue,dueKind,dueLabel,rxLink}, …≤50] }
        │
        ├─ renderMyTasks(): all + loadPins() → [закреплённые 📌] + [авто-добор] → карточки (≤5)
        └─ openMyControl(): all + loadPins() → список с 📌-переключателями
                                   │ togglePin(id) → savePins() → re-render блок + модалка
localStorage: armgov.mycontrol.<userId> = [id, …]
```

## Обработка ошибок / краевые случаи

- **Пин на завершённое задание:** отсутствует в `all` → отбрасывается и чистится из localStorage (самозаживление).
- **localStorage недоступен / битый JSON:** `try/catch`, деградация до пустого списка пинов (как в `loadLayout`).
- **Инбокс > 50:** модалка показывает первые 50 по срочности; закреплённые вне топ-50 всё равно рендерятся в блоке (их id в пинах, но данных нет → выпадут). Приемлемо для демо; если станет проблемой — поднять кап. (Ограничение зафиксировано осознанно.)
- **Fetch упал:** прежнее поведение — блок пустой (`catch`).

## Проверка

Прототип — статик + локальный сервер (`/run`). Ручной сценарий:
1. Открыть стартовую, блок «Мои задания» показывает авто-топ (как раньше).
2. «⚙ Настроить контроль» → модалка со списком активных заданий.
3. Закрепить 2 задания → они появляются сверху блока с 📌, авто-добор заполняет остальное.
4. Перезагрузить страницу → пины сохранились.
5. Снять пин → задание уходит из закреплённых.
6. (Если воспроизводимо) завершённое ранее закреплённое задание не показывается и вычищается из пинов.

## Вне области

- Перенос в RX-native (отдельный цикл после подтверждения на демо).
- Реальная многопользовательность (демо-юзер захардкожен).
- Контроль чужих объектов/документов вне своего инбокса.
