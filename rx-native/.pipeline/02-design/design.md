# RX-native ARMGov — Design (нативная реализация в Directum RX)

Дата: 2026-06-26. Статус: дизайн (деплой — позже). Папка проекта: `rx-native/` внутри репозитория
прототипа. **Прототип (`Program.cs`/`index.html`) не трогаем — он для демо.**

## 1. Цель и направление
Перенести ценность ARMGov в **нативную среду Directum RX**, написав **с нуля**:
- **Гибрид:** нативный модуль RX (обложка) + богатый UI как **Remote Component (React)** в scope `Cover`.
- Данные — **самодостаточно**: server-функции модуля считают метрики сами (без зависимости от PrAnlts/PrBI,
  т.к. их нет на стенде) через платформенный SQL-API + `Cache`.
- Авторизация/права — нативные (сессия RX + роли модуля). Отдельный хостинг/токен не нужны.

## 2. Журнал решений (зафиксировано с заказчиком)
- Способ: **гибрид** — нативная обложка + RC в обложке. (не iframe внешнего веб-аппа)
- Прототип за основу **не берём** (он бьёт по БД прямым тяжёлым SQL); переиспользуем **логику метрик** и продуктовые решения.
- Источник данных: **самодостаточно в ARMGov** (server-функции; без PrBI).
- Авторизация: наследуется от RX-сессии (RC).
- Первая итерация: **сквозной скелет** (вертикальный срез всего конвейера на одном блоке).
- Сейчас: **только проектирование**; деплой позже (нужен чистый стенд + admin-UAC + бэкапы).
- Расположение: отдельная папка `rx-native/` в репо прототипа; документация по пайплайну.

## 3. Идентичность модуля (по правилам RX — `ds_moduleeditor_maintab`)
- **Имя (Name):** `ARMGovDash` — уникально в рамках кода компании, латиница+цифры, с буквы.
  Используется в коде; полное обращение — `DirRX.ARMGovDash`.
- **Код компании (CompanyCode):** `DirRX` (как у PrBI/PrAnlts/прежнего ARMGov).
- **Отображаемое имя (DisplayName):** **«АРМ Руководителя»** — видно в проводнике системы; локализуемое
  (`Module.ru.resx`; валидатор Check9 требует ключ DisplayName). ds рекомендует короткое имя — подходит.
- **Имя в БД:** 2–7 символов, латиница, с буквы, уникально (предлагаю `ARMGD`) — задать явно.
- **Свежий GUID** (НЕ переиспользуем старый `DirRX.ARMGov`), чтобы не тащить «крашевую» метадату (obj/enum, см. research).
- **Без enum-свойств** в первой версии (прошлый краш был на enum `Code=null`). Если настройка нужна —
  булевы/числовые/ссылочные свойства, либо enum строго через DDS-редактор с непустыми `Code`.

## 3.1 Слой разработки (⚠️ важно — не публиковать в базовый слой)
RX различает **слои разработки** (тип репозитория `@solutionType`): **`Base`** — платформенный/стандартный
слой (туда **НЕ публикуем**), **`Work`** — слой разрабатываемого решения (наш). Источники:
`ds_nastroyka_repozitoriyev`, гайды 27/34.

- **ARMGovDash публикуем в слой `Work`** отдельным **applied-solution пакетом (.dat)** (эталоны: Targets, OmniApplied).
- Базовые/стандартные модули (`Sungero.*`, гос-решение) — **предыдущий слой** (`IsPreviousLayerModule=true`):
  зависим и наследуемся, но **не публикуем в них** и не модифицируем.
- **PackageInfo.xml:** ровно один корневой модуль `IsSolution=true`, остальные — через `SolutionId`.
  Оптимум для нашего объёма: `DirRX.ARMGovDash` — сам корень решения (`IsSolution=true`, один модуль-решение).
  При росте — выделить тонкий solution-root + функциональные модули (как `DirRX.DirectumTargets` + DTCommons/KPI).
- ⚠️ Прошлый `DirRX.ARMGov` чекаутился под `git_repository/base/...`. У нас исходники и публикация — **строго в
  Work-слой/репозиторий**, НЕ в Base. (Часть прошлых проблем — от смешения со стандартным слоем.)
- Деплой — отдельным .dat (DeploymentTool/DTC), зависимости на платформу — через previous-layer, без правок Base.

## 4. Архитектура
```
Directum RX Web Client (Host)
  └── Обложка модуля DirRX.ARMGovDash
        └── Remote Component "ArmGovDashboard" (React, scope Cover)
              ├── рендерит KPI/светофор/treemap/прогноз/тематики
              └── data: вызовы server/public-функций модуля (в сессии RX)
ARMGovDash.Server (C#)
  ├── PublicFunctions: GetRegionOverview / GetProcess / GetAppealTopics / ... (DTO = Structures)
  ├── данные: платформенный SQL-API (SQL.CreateConnection / Queries.xml) по sungero_wf_*/gd_citizen
  ├── Sungero.Core.Cache (TTL) — кэш агрегатов (аналог кэша прототипа)
  └── Roles (ARMManager/ARMAdmin), ModuleInitializer (идемпотентный)
```

### 4.1 Слой данных (ключевое — «не бить БД»)
- Переносим **логику** SQL прототипа (overview, process, тематики обращений, прогноз, исключение
  уведомлений, имена этапов) в server-функции.
- Доступ к БД — **платформенный SQL-API** (`SQL.CreateConnection`/`Queries.xml`), НЕ `System.Data`.
- Тяжёлые агрегаты — за `Cache.AddOrUpdate(key, struct, ttl)` (TTL ~60с, как в прототипе). Никаких
  `GetAll().Count()` без `Where`. Запрос по требованию (открытие обложки/refresh кнопкой), не на каждый чих.
- DTO между сервером и RC — **Structures** (анонимные типы запрещены), сериализуются в JSON для RC.

### 4.2 Remote Component (UI)
- React + Module Federation, scope `Cover`; эталоны — CRM RC (`DirRX-CRMComponents`) + гайд 26.
- Singleton React в shared; `--rndx-theme_*` для тем; i18next ru/en.
- Данные RC получает вызовом функций модуля (через OData/PublicApi хоста — **уточнить точный путь
  RC→server на этапе скелета**, см. §7 open items).
- Графику (treemap/спарклайн/бары) переносим как React-компоненты (логику отрисовки берём из прототипа).

### 4.3 Доступ/роли
- Роли `ARMManager`/`ARMAdmin`; права на обложку/модуль — NoCode после деплоя (конвенция платформы).
- Поиск ролей — по `Sid` (не `IncludedIn(Guid)`).

## 5. Первая итерация — «сквозной скелет» (вертикальный срез)
Цель: пройти **весь конвейер** на одном блоке, до того как наращивать.
1. Каркас модуля `DirRX.ARMGovDash` (Module.mtd, Constants, роли, ModuleInitializer) — чисто, без enum.
2. **Одна** server-PublicFunction (напр. `GetRegionKpi`) → Structure с 3–4 числами (всего/в работе/просрочено),
   данные через SQL-API + Cache.
3. **RC в обложке** (минимальный React), рендерит эти числа из вызова функции; интеграция темы.
4. Сборка RC (node/webpack) + упаковка в модуль (Components).
5. (позже, когда стенд готов) деплой от admin-UAC, бэкап до/после, smoke: обложка рисуется, числа отдаются,
   WebServer стабилен (без `same key`).

Только после зелёного скелета — наращиваем блоки (светофор, процесс, тематики, прогноз, ИИ).

## 6. Что необходимо (prereqs)
- Чистый стенд RX + admin-UAC для деплоя (позже). Бэкап БД до/после.
- node/npm — есть. MCP-toolchain (scaffold/validate/deploy) — поднять в HANDOFF-воркспейсе.
- Эталоны RC (CRM) и гайды — на месте.
- Не разворачивать PrAnlts/PrBI (самодостаточны).

## 7. Открытые вопросы (решить на скелете)
- Точный путь **RC → server-данные**: OData-функция vs PublicApi vs `[Public]` server-function — выбрать на скелете
  (эталон — как CRM RC получает данные).
- Подтвердить имя модуля `DirRX.ARMGovDash` и базовый GUID.
- Где физически собирать RC и как класть в `Components` модуля (по эталону CRM).
- **Слой Work:** отдельное самостоятельное решение `DirRX.ARMGovDash` (рекомендую — изоляция) vs включение
  в существующее applied-решение Work-слоя. Подтвердить репозиторий/папку `Work` и `@solutionType: Work`.

## 8. Соответствие антипаттернам
Дизайн обязан пройти чек-лист из `01-research/research.md` (канон «9 запретов» + perf + уроки PROJECT-HISTORY):

## 10. Реюз из прототипа (только логика, не код)

прогноз по тренду, отсечение будущих месяцев. **Код C#/JS прототипа не копируем** — переписываем под нормы RX.
