# Харнес аналитики: SQL, проверяемые результаты и отчёты

Дата: 2026-09-19. Статус: пользователь разрешил подготовку детального плана 2026-09-19; реализация ещё не начата.
Владелец: Коротаев Н.О. Читатель: владелец продукта и разработчик; решение — границы реализации харнеса.
Класс: артефакт архитектурного решения. База анализа: `analytics-canvas`, коммит `5494232`.

## 1. Цель и подтверждённые требования

Пользователь задаёт вопрос на русском языке. Модель самостоятельно исследует доступную схему, генерирует SQL, получает данные из Directum RX и предлагает отчёт. Приложение выполняет только чтение БД и строит числовые показатели, таблицы и графики из результатов реально выполненных запросов.

Подтверждено пользователем: read-only к БД; гибкая аналитика с генерацией запросов моделью; преобразование результатов в отчёты; работа по процессу Superpowers. Текущий провайдер — GigaChat-2. Поддержка Qwen должна сохраниться.

Принятые для этой спецификации допущения: сохраняем .NET 10, HttpListener, Npgsql и существующий браузерный клиент; интерфейс первой поставки — текущая «Аналитика по запросу»; отчёт означает интерактивные таблицы, показатели и графики в приложении. DOCX/PDF, расписание отчётов и постоянное хранилище результатов относятся к следующим поставкам.

## 2. Наблюдаемые ограничения текущей реализации

Проверено чтением `Program.cs`, `index.html`, `charts.js`:

- `LlmChatCore` передаёт обычные сообщения и читает `message.content`; нативные функции GigaChat не передаются и не разбираются.
- `SqlAgentAsk` извлекает JSON из текста, допускает окончательный `answer` без получения релевантного результата. Наличие текста не подтверждает числа в нём.
- Промпт требует готового инструмента для любого вопроса с периодом; `leaders` и `leader_tasks` периода не принимают.
- Хранятся только последний результат инструмента и последний результат SQL. `chart.from` не идентифицирует конкретное исполнение.
- В агентском SQL-шаге выдача ограничена 50 строками; внешний исполнитель допускает 200. Значения строк и коллекций также обрезаются.
- `SchemaHelp` ограничивает колонки первыми 80, примеры первыми 40; каталог не является полноценным описанием бизнес-смысла.
- История Canvas сохраняется в памяти браузера; запрос отправляет только текущий вопрос, без предыдущих результатов.
- Уже имеются SqlCheck, read-only транзакция, statement_timeout, ограничения результата, локальная граница доступа и чистые функции визуализации. Их сохраняем и покрываем регрессиями.

Числа «12 и 8» из пользовательского примера не принимаются за эталон. Эталон определяется независимым SELECT на момент проверки.

## 3. Рассмотренные подходы

1. Исправить только JSON-промпт. Минимальная стоимость, но сохраняются неподтверждённые ответы и привязка к последнему результату. Не соответствует цели.
2. Модульный харнес в текущем приложении: адаптер модели, каталог, единый исполнитель SQL, реестр результатов, проверка отчёта. Рекомендуемый подход; позволяет выпускать изменения постепенно.
3. Отдельный агентный сервис, аналитическая БД и очередь заданий. Уместно при многопользовательской нагрузке, но добавляет инфраструктуру до проверки гипотезы. В первую поставку не входит.

## 4. Архитектура и границы модулей

Поток: вопрос → интерпретация метрики/периода → поиск сущностей и схемы → SQL → проверка → read-only исполнение → результат с ID → предложение отчёта → проверка ссылок → рендер.

Разделение по ответственности, без переноса несвязанных билдеров дашборда:

| Модуль | Ответственность |
|---|---|
| `Harness/Models` | Общие контракты вызова, результата, отчёта и ошибки |
| `Harness/Providers` | Адаптер GigaChat и адаптер существующего текстового протокола Qwen |
| `Harness/Catalog` | Смысл метрик, таблицы, связи, доступные поля и разрешённые области данных |
| `Harness/Execution` | Политика SQL, соединение, транзакция, лимиты и отмена |
| `Harness/Agent` | Состояние одного запуска, инструментальные шаги и исправление ошибок |
| `Harness/Results` | Реестр фактических результатов и безопасные проекции для модели |
| `Harness/Reports` | Проверка спецификации отчёта и подстановка фактических значений |
| `Program.cs` | HTTP-маршруты, конфигурация и адаптация существующих билдеров |

Названия файлов и точные сигнатуры закрепляются в плане реализации после рассмотрения спецификации. Выделение модулей ограничено харнесом; миграции всего приложения на новый фреймворк нет.

## 5. Только чтение и управляемая нагрузка

Каждый сгенерированный запрос проходит одну общую политику, независимо от провайдера и HTTP-маршрута. Отклоняются несколько операторов, запись, DDL, опасные функции и обращения за пределы разрешённого каталога. Разрешены чтение, CTE, объединения, агрегаты и оконные функции в рамках политики.

Ни модель, ни её аргументы не управляют строкой подключения, правами, таймаутами и списком разрешённых объектов. Тексты из БД — данные, а не инструкции; они не изменяют системные правила или каталог инструментов.

Выполнение: явная read-only транзакция; statement_timeout 10 секунд; не более двух одновременно исполняемых запросов харнеса; ожидание слота входит в общий бюджет запуска. Общий бюджет — 120 секунд, до восьми обращений к модели, из них не более двух повторов после ошибки протокола или отчёта. Все ожидания и обращения провайдера получают остаток бюджета и CancellationToken. Завершение бюджета даёт состояние incomplete, а не свободно сгенерированный «успешный» ответ.

Разделяются:
- SQL, предложенный моделью;
- проверенный эффективный SQL с серверными ограничениями;
- параметры и результат исполнения.

Для эксплуатационной поставки обязательна отдельная роль БД с минимальными правами SELECT на разрешённые объекты, без прав записи и создания объектов; отдельно проверяются наследуемые права и доступ к функциям. Роль не должна быть superuser или владельцем рабочих объектов. Изменения ролей, GRANT/REVOKE и DDL в БД RX приложение не выполняет. Подготовка роли — административная зависимость, не скрытая операция агента. Текущую конфигурацию можно использовать для локальной проверки совместимости; это не подтверждение изоляции прав.

Полноценный PostgreSQL AST-валидатор выделяется в следующую поставку. До его внедрения сохраняется текущий валидатор и добавляются тесты новых путей; никакой текстовый валидатор не объявляется доказательством безопасности. Внедрение AST потребует выбора поддерживаемого .NET/Windows-совместимого решения и отдельного плана.

## 6. Каталог, метрики и поиск сущностей

Каталог содержит сущности и разрешённые таблицы/колонки, связи и кардинальность, значения статусов, определения метрик, временные поля и исключения. Первое наполнение извлекается из существующих SchemaCore и билдеров, а не придумывается заново.

Модель получает инструменты поиска по каталогу, описания выбранных таблиц и поиска сотрудников. Описания выбираются по нужным полям, а не по первым ordinal_position. Схема БД указывается явно, чтобы одноимённые таблицы разных схем не смешивались. Примеры значений выдаются только для разрешённых полей и в ограниченном объёме.

Поиск сотрудника возвращает ID, ФИО и подразделение. Используется параметризованный SELECT; модель не передаёт готовый SQL в этот инструмент. Несколько кандидатов требуют уточнения, отсутствие кандидата возвращается явно. Имена в косвенных падежах модель переводит в поисковые варианты; выбор ID разрешён только из фактически найденных кандидатов.

Бизнес-правила:
- «Поручение» и «задание» — разные единицы подсчёта. Для персонального количества поручений используется согласованная с дашбордом дедупликация корневых задач.
- «Количество поручений» не означает «выполнено». По умолчанию в этом сценарии считаются все поручения выбранного периода, определение показывается в отчёте.
- «За 12 месяцев» означает скользящий интервал 12 месяцев, заканчивающийся временем запуска. В первой поставке фильтр поручений относится к дате создания корневого поручения; вопросы о завершении фильтруются по дате завершения, что явно отображается.
- Стандартные KPI используют существующие определения, классификацию процессов и исключение уведомлений.
- Если вопрос целиком закрывается готовой метрикой, используется её билдер. Для отсутствующего среза допускается генерация SQL, в том числе для периода или сравнения сотрудников.

Логическая корректность произвольного SQL не гарантируется валидатором. Её обеспечивают определения, отображение принятой интерпретации, контрольные сценарии и возможность проверить запрос.

## 7. Протокол модели и инструменты

Общий внутренний результат обращения модели — набор из одного действия: вызов инструмента, предложение отчёта, запрос уточнения либо структурированная ошибка. Неизвестное имя и неверные аргументы не исполняются; исправление расходует бюджет.

GigaChat: передаём JSON Schema функций через `functions`, читаем `message.function_call`, сохраняем `functions_state_id`, возвращаем результат сообщением `role=function`. Обычный текст от модели не становится числовым отчётом в обход проверки. История сохраняет реально возвращённые вызовы и результаты. OAuth, кэш токена и обновление при 401 остаются серверными, входят в бюджет вызова.

Qwen: существующий текстовый JSON преобразуется в те же внутренние действия; все проверки результатов и отчётов общие. Нативный протокол Qwen можно добавить отдельно.

Инструменты: поиск каталога, описание таблиц, поиск сотрудников, существующие готовые метрики, выполнение проверенного SQL, чтение страницы ранее полученного результата, предложение отчёта, запрос уточнения. Модель не получает инструменты записи, исполнения кода или произвольного HTTP-доступа.

## 8. Реестр результатов

Внутри запуска хранится каждый успешный результат с `runId` и уникальным `resultId`, источником, SQL/параметрами, определением среза, временем получения, колонками и типами, строками, предупреждениями и флагами усечения.

Ограничения первой поставки: до 200 строк, 60 колонок и 1 МиБ сериализованного результата на исполнение; до 4 МиБ на запуск. Превышение лимита байтов останавливает накопление с явным предупреждением. Ограничение сериализации не гарантирует ограничение памяти Npgsql для одной большой ячейки; запреты опасных/неограниченных конструкций и ограничения БД остаются отдельным рубежом.

Модели передаются описание и первые 20 строк, продолжение доступно отдельным инструментом. Для строк, колонок и ячеек сохраняются разные признаки усечения. Усечённое текстовое поле не используется для идентификации сотрудника; ID сохраняется отдельно. Усечённый результат нельзя представлять как полный рейтинг или использовать как полный знаменатель долей.

Первая поставка хранит реестр только до завершения запроса; клиент получает проверенные проекции для показа и своей текущей истории. Ссылки на другие запуски запрещены. Постоянное хранение, продолжение предыдущего исследования и экспорт за пределы лимита — отдельная поставка.

## 9. Проверяемый отчёт

Спецификация отчёта содержит заголовок, интерпретацию вопроса, период, определения метрик и блоки: таблица, столбики, линия, доли, KPI. Каждый блок ссылается на `resultId` и существующие колонки; строковые фильтры ссылаются на устойчивые ключи результата. Произвольные числовые массивы от модели не принимаются.

Числовые факты в тексте задаются ссылками на строку/колонку или типизированными операциями над результатом: сумма, разность, отношение. Операции рассчитывает сервер; деление на ноль даёт «нет данных». Поддерживаемый шаблон текста содержит идентификаторы фактов, которые подставляет сервер. Произвольный текстовый комментарий отделён от подтверждённых показателей; он не получает статус проверенного заключения и не используется как источник графиков.

Валидация проверяет существование источника и полей, совместимость типов с видом графика, ссылки фактов, допустимость операций, усечение. Неправильный отчёт возвращается модели для исправления. Неисправленный отчёт не показывается как успешный: пользователь видит понятную причину и доступную фактическую таблицу, если её можно показать без ложной интерпретации.

Состояния ответа: completed, needs_clarification, no_data, incomplete, failed. Пустая выборка отличается от отсутствующего источника; SQL-ошибка — от нулевого количества. При неподтверждённых данных нельзя возвращать успешный свободный числовой ответ.

## 10. HTTP и интерфейс

Старые эндпоинты и сводки сохраняются. Новый контракт получает отдельный маршрут `POST /api/ai/analysis`, локальная проверка доступа такая же, как у SQL-харнеса. Переход Canvas на него производится после серверных тестов. Старый `/api/ai/sql` остаётся для совместимости и сравнительных проверок, но не объявляется защищённым новым контрактом отчётов.

Ответ содержит runId, status, interpretation, report, проверенные проекции datasets, steps, elapsedMs и warnings. Уточнение содержит question и проверенные варианты сущностей; повторная отправка включает исходный вопрос и выбранные ID, которые сервер повторно проверяет.

В интерфейсе показываются: что посчитано, период, источники, предупреждения, таблица и допустимые графики. Не выводим пользователю внутреннее `chart.from=""` как итоговый результат. В «Ходе анализа» показываем вызовы, параметры, длительность и ошибки; скрытые рассуждения модели не являются контрактом и не запрашиваются.

## 11. Проверки и критерии приёмки

Основные автоматические проверки выполняются без живой модели и без доступа к RX: подставной HTTP-провайдер, фиксированные результаты инструментов и тестовая БД для read-only. Проверки с GigaChat и RX запускаются отдельно и имеют собственный результат; недоступный провайдер не считается успешной проверкой качества.

| Сценарий | Ожидаемое поведение |
|---|---|
| Нативный вызов GigaChat | Функция и аргументы исполнены один раз; сохранён functions_state_id; результат передан с правильной ролью |
| Неверные аргументы, пустой content, 401 | Исправление либо понятная ошибка в бюджете, без выдуманного отчёта |
| Ответ «12 и 8» без источников | Отчёт отклонён; числа не показываются как факты |
| Неизвестный resultId или колонка | Ошибка валидации и ограниченное исправление |
| Несколько запросов | Отчёт может ссылаться на любой результат текущего запуска, а не только последний |
| Два однофамильца | Уточнение с реальными кандидатами, без произвольного выбора |
| Сотрудник отсутствует | Явное отсутствие; не подмена нулём поручений |
| Несколько заданий одного поручения | Персональный подсчёт не удваивает поручения |
| Пограничная дата периода | Одинаковая граница в запросе и подписи отчёта |
| Усечение строк/колонок/ячеек | Видимое предупреждение, отсутствие ложных полных итогов |
| Таймаут или отмена | Прекращается текущая работа; возвращается incomplete/failed, без свободного финального вымысла |
| DML/DDL, несколько операторов, опасная функция | Отклонение до исполнения; проверка реальной роли проводится отдельно |
| Старые графики и сводки | Регрессии smoke и charts отсутствуют |

Живой приёмочный вопрос: «Сравни количество поручений у Ивана Иванова и Босова Александра за 12 месяцев». Результат принимается, если личности разрешены однозначно либо задано уточнение; видны метрика и даты; данные совпадают с независимым контрольным SELECT; таблица, показатели и график используют один и тот же источник. Отсутствие сотрудника на стенде — допустимый no_data/needs_clarification, а не повод синтезировать результат.

## 12. Последовательность поставок

Это границы работ, не детальный план реализации Superpowers.

1. **Первая сквозная поставка:** общий протокол и нативный GigaChat, ограниченный каталог и поиск сотрудников, контролируемый SQL, реестр результатов, проверяемый отчёт, подключение Canvas, регрессионные и живые проверки. Qwen остаётся совместимым адаптером. Проверка эксплуатационных прав оформляется отдельно от локального запуска.
2. **Усиление эксплуатации:** PostgreSQL AST-политика, применение подготовленной администратором роли, нагрузочные проверки, права пользователей при выходе за локальный режим. Без этого первая поставка не объявляется промышленной.
3. **Развитие отчётов:** постоянное хранение и повтор запуска, продолжение исследований, DOCX/PDF, большие выборки и фоновые задания. Потребует отдельной спецификации.

После подтверждения этой спецификации создаётся детальный план первой поставки: точные файлы и контракты, red/green-тесты, небольшие проверяемые задачи, ревью и контрольные коммиты. Затем пользователь рассматривает план и выбирает исполнение с субагентами либо в основной сессии, как требует Superpowers 6.4.1.
