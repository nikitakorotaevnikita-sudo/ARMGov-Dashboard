# Разведка: соисполнители поручений в модели данных RX

**Дата:** 2026-08-10
**Зачем:** эпик 8 роадмапа (P0). Метрика «под риском» показывает ответственному исполнителю
неверное значение, потому что не учитывает соисполнителей. Требование заказчика — CustDev №2,
Ильина А.А., 29.07.2026.
**Инструмент:** `tools/dbq` против стенда `DirRX261OGVGenAI`. Только `SELECT`.

**Итог: метрика считается. Данные для неё на стенде есть.** Ниже модель, проверенный SQL и три
нюанса, которые обязательно учесть при реализации.

---

## 1. Модель данных

| Что | Где |
|---|---|
| Ответственный исполнитель поручения | `sungero_wf_task.assigneetai_recman_sungero` |
| Соисполнители простого поручения | `sungero_recman_taicoassignees (task, assignee, assignmentcrea)` |
| Пункты составного поручения | `sungero_recman_taiparts (task, assignee, deadline, number, aiparttask, supervisor, …)` |
| Соисполнители пункта | `sungero_recman_taipartscoasgs (task, coassignee, partguid)` |
| Задания | `sungero_wf_assignment (task, performer, status, deadline, completed)` |

**Ключевое: задания соисполнителей лежат не на головной задаче, а в дочерних.** Связь — через
`sungero_wf_task.maintask`. Головная задача ссылается на себя (`maintask = id`), дочерние — на неё.
Поле `parenttask` в этих данных не заполнено; `parentasg` указывает на задание ответственного,
из которого выросла подзадача.

Наивный `join` заданий по `task = <головная задача>` **не находит ничего** — это и есть причина,
по которой метрика сейчас слепа к соисполнителям.

### Проверено на примере — задача 594

| Задание | Задача | Исполнитель | Статус | Срок | Роль |
|---|---|---|---|---|---|
| 786 | 594 | Босов Александр | Completed (01.08) | 31.08.2023 | ответственный |
| 789 | 594 | Концева Надежда Ивановна | Completed | — | на головной задаче |
| 787 | **585** | Федоров Федор Александрович | InProcess | 30.08.2023 | соисполнитель |
| 788 | **610** | Фомин Александр | InProcess | 30.08.2023 | соисполнитель |

Ответственный свою часть закрыл, оба соисполнителя — нет. Это буквально кейс из интервью:
«мне при этом закрываться нечем».

## 2. Рабочий запрос

Сводка по ответственным: сколько у них соисполнителей и сколько из них не укладывается в срок.

```sql
with head as (
  select t.id, t.assigneetai_recman_sungero as resp
  from sungero_wf_task t
  where t.assigneetai_recman_sungero is not null
    and t.maintask = t.id
),
co as (
  select h.id as task_id, h.resp, ca.assignee as co_id,
         a.status::text as co_status, a.deadline as co_deadline, a.completed as co_completed
  from head h
  join sungero_recman_taicoassignees ca on ca.task = h.id
  left join sungero_wf_assignment a
         on a.performer = ca.assignee
        and a.task in (select id from sungero_wf_task where maintask = h.id)
)
select r.name,
       count(*) as vsego,
       count(*) filter (where co_completed is null
                          and co_deadline < now()
                          and co_status <> 'Aborted') as prosrocheno
from co
join sungero_core_recipient r on r.id = co.resp
group by r.name
order by prosrocheno desc;
```

Результат на стенде (данные 2023 года, поэтому всё активное просрочено):

|---|---|---|
| Иванов Иван Иванович | 6 | 5 |
| Босов Александр | 4 | 4 |
| Концева Надежда Ивановна | 6 | 3 |

## 3. Нюансы, обязательные к учёту

**1. `Aborted` нельзя считать просрочкой.** Распределение статусов заданий соисполнителей:

| Статус | Всего | Из них подошли бы под наивную «просрочку» |
|---|---|---|
| InProcess | 13 | 13 |
| Completed | 6 | 0 (у 4 из них срок вообще не задан) |
| **Aborted** | **3** | **3** |
| нет задания | 1 | 0 |

Наивное условие `completed is null and deadline < now()` затягивает три прерванных задания.
Это согласуется с существующей логикой прототипа: в воронке «прервано» — отдельная категория,
а не просрочка. В запросе выше исключение уже добавлено.

**2. Соисполнитель без задания.** Один случай: запись в `taicoassignees` есть, задания нет,
`assignmentcrea` пустой. Нужно решить, как показывать — «задание не создано» отдельным
состоянием, а не молча пропускать: с точки зрения ответственного это тоже риск.

**3. `deadline` бывает `null`** — у 4 из 6 завершённых. Любое сравнение со сроком должно быть
устойчиво к `null`, иначе задание молча выпадает из знаменателя.

**4. Уведомления.** Запрос выше их не исключает. В реализации обязательно применить общее правило
проекта — вычитание типов `*Notice`/`*Notification` (`NoticeNotIn` в `Program.cs`).

**5. Охват.** Из 47 записей в `taicoassignees` под условие «головная задача с назначенным
ответственным» попадают 23. Остальные относятся к задачам другой структуры — при реализации
проверить, не теряется ли значимая часть.

## 4. Что это меняет в метрике

Сейчас «под риском» для пользователя считается только по его собственным подчинённым и заданиям.
После доработки для роли **ответственного исполнителя** появляется второе слагаемое: состояние
соисполнителей по тем поручениям, где он ответственный.

Показывать имеет смысл раздельно, а не суммой: «мои — N, соисполнители — M». Слитая цифра снова
скроет причину, а весь смысл требования в том, чтобы отделить «я не успеваю» от «мне не сдают».

## 5. Побочная находка для эпика 10

В `sungero_recman_taiparts` есть поле **`supervisor`** — контролёр на уровне пункта поручения.
Это прямой заход к метрике «задержка на контроле» из эпика 10: разделить «исполнитель сдал» и
«контролёр принял» можно, не изобретая эвристик. Отдельной разведки не делал.
