# ИИ-харнесс запросов к БД и выравнивание фронтенда — дизайн

**Дата:** 2026-09-15
**Проект:** ARMGov-Dashboard (прототип проверки гипотез)
**Автор постановки:** Никита Коротаев
**Эталон:** `presale-dashboard` (`src/code_agent.py`, `src/agent_sandbox.py`, `static/tokens.css`, `static/style.css`)

## 1. Задача

Две независимые части в одном прототипе.

**Харнесс.** Сегодня ИИ-чат работает по «подходу A»: весь JSON метрик кладётся в системный промпт, модель только интерпретирует готовые числа. Это надёжно, но отвечает лишь на то, что уже посчитано дашбордом, и стоит 35 секунд на вопрос (замер 15.09.2026; причина — длина ответа, а не размер промпта, см. §2). Нужен режим, в котором модель сама достаёт данные из базы RX: произвольные срезы, кросс-расчёты, вопросы, которых нет в сводке. Числа в ответе должны браться из фактически выполненного запроса, а не из «памяти» модели.

**Фронтенд.** Прототип и presale-dashboard должны выглядеть одним продуктом. Токены уже общие — `tokens.css` в обоих проектах побайтово одинаков, `data-theme="state-1"` выставлен, хардкод-цветов осталось 12. Расходится слой компонентов и типографика.

## 2. Решения по объёму (согласованы)

| Развилка | Решение |
|---|---|
| Что исполняет харнесс | Сырой `SELECT` к базе RX |
| Граница безопасности | Валидатор в коде + read-only транзакция (отдельную учётку БД не заводим) |
| Схема для модели | Ручной словарь ядра (10–15 таблиц) + действие «справка по таблице» |
| Архитектура цикла | Многошаговый агент (вариант B), до 5 шагов |
| Место в UI | Тумблер в существующем дровере «Спросить ИИ» |
| Источники данных | Готовые инструменты (сборщики дашборда) + `sql` для срезов, которых они не дают |
| Показ хода | Один JSON с протоколом шагов; в чате — раскрывающийся блок размышлений |
| Шрифт Inter | Вшить локально, без Google Fonts |
| Глубина выравнивания | Компоненты и типографика; экраны и навигация не трогаются |

### Что стоит времени (замеры 15.09.2026, Qwen3.8-27B на Ario)

| Изменение | Результат |
|---|---|
| Промпт 44 → 8623 токена | 0,7 → 1,4 с |
| Вывод 100 / 300 / 800 токенов | 3,0 / 11,1 / 23,3 с |

**Скорость генерации ~30 токенов/с; размер промпта практически ничего не стоит.** 35 секунд нынешнего чата дают не метрики в промпте, а ответ на 1000 токенов.

Два следствия для дизайна, и оба существенные:

1. **Готовые данные в промпт можно класть щедро** — отсюда предзагрузка сводки и каталог инструментов (§5).
2. **Платим за то, что модель пишет.** Шаг с мыслью и SQL — 150–250 токенов вывода, это 5–8 с; финальный ответ на 300 токенов — ещё 10 с. Типичный вопрос: два шага плюс ответ ≈ 25 с. Отсюда бюджет: **5 шагов, 60 секунд** — шестой шаг при таком темпе всё равно не успевает. *(17.09.2026: расчёт остался верным, но потолок времени поднят до 120 секунд — на многошаговых вопросах часть ответов упиралась в него и доходила с пометкой «не уложился». Число шагов не менялось.)*

## 3. Ограничения

- .NET 10, `HttpListener`, Npgsql, `System.Text.Json`; вся логика в `Program.cs`, фронтенд в `index.html` — архитектуру прототипа не меняем.
- **Только `SELECT`** — нерушимое правило проекта (`CLAUDE.md` §1). Харнесс не имеет права его ослабить.
- Секретов в коде нет; токен LLM и пароль БД — только в `config.json` рядом с exe.
- Уведомления (`*Notice`/`*Notification`) исключаются из статистики — правило должно попасть в промпт агента.
- Общение с пользователем и весь UI — по-русски.

## 4. Компоненты

```
Program.cs
├── SqlGuard.Check(sql)   → {ok, reason, effective}   — валидатор, без побочных эффектов
├── SqlGuard.Run(sql)     → {cols, rows, ms}          — исполнитель в read-only транзакции
├── ToolRegistry.Call(name, args) → JSON                — девять готовых инструментов (§5)
├── SqlAgent.Ask(messages)→ {reply, steps, elapsedMs}   — цикл агента
├── SchemaDict            — словарь ядра + справка по таблице из information_schema
└── эндпоинты: POST /api/ai/sql, GET /api/ai/sql/check

index.html
├── тумблер «Глубокий анализ (SQL)» в дровере чата
└── блок «Размышления · N шагов · T с» — раскрывается в ленту шагов

style.css (новый)  — стили, вынесенные из index.html, + компоненты по presale
static/inter-*.woff2 — шрифт локально
```

Каждая единица — одна ответственность и проверяется отдельно: валидатор через `/api/ai/sql/check` без похода в базу, исполнитель — на заведомо корректном запросе, цикл — на живом вопросе.

## 5. Инструменты и маршрутизация

### Почему инструменты вообще нужны

Нерушимое правило проекта — метрики должны сходиться друг с другом. Если чат скажет «просрочено 812», а на экране 810, прототип теряет доверие немедленно, и никакие объяснения про «другой срез» не помогут. Поэтому ключевые цифры агент **не считает сам**, а берёт у тех же сборщиков, которые рисуют экран: они уже исключают уведомления, уже кэшируются (TTL 60 с) и уже содержат определения метрик — воронку, соблюдение сроков, пороги.

### Каталог (девять инструментов)

| Инструмент | Источник | Закрывает |
|---|---|---|
| `overview(period)` | `BuildOverview` | KPI по всем процессам: в работе, срок сегодня, просрочено, соблюдение сроков |
| `process(key, period)` | `BuildProcess` | Воронка и здоровье процесса: поручения, обращения, НПА |
| `leaders(by)` | `BuildLeaders` | Исполнение по сотрудникам / подразделениям / НОР, включая `coOverdue` |
| `leader_tasks(by, id)` | `BuildLeaderTasks` | Проваливание до конкретных задач сотрудника или подразделения |
| `stuck(key, period)` | `BuildStuck` | Где застревает работа, долгострои |
| `by_kind(key, period)` | `BuildByKind` | Разрез по видам поручений |
| `departments(key, period)` | `BuildDepartments` | Разрез по подразделениям |
| `my_tasks()` | `BuildMyTasks` | Личный контроль руководителя |
| `appeal_topics()` | `BuildAppealTopics` | Тематики обращений граждан |

`appeal_topics` в списке не ради удобства: тематики собираются эвристиками по тексту, в базе такого поля нет — SQL-агент их не воспроизведёт в принципе.

Остальные эндпоинты (`workload`, `dept_tasks`, `kind_tasks`, `performer`, `task`) инструментами не делаем: они достижимы через `sql`, а меню из девяти пунктов модель ещё выбирает осмысленно, из двадцати — уже нет.

### Как решается «инструмент или SQL»

Три слоя, от дешёвого к жёсткому.

1. **Каталог и правило в промпте.** У каждого инструмента — описание, что он возвращает, и правило: *если вопрос закрывается инструментом, вызвать инструмент обязан; `sql` разрешён только для среза, которого не даёт ни один инструмент*. Плюс около десяти примеров «вопрос → чем отвечать».
2. **Предзагрузка без участия модели.** До первого обращения к LLM код сам кладёт в контекст `overview` и `processes`. Замер (§2) показывает, что это порядка +6 тыс. токенов и +0,3 с — то есть почти даром. Самые частые вопросы («сколько просрочено», «какой процесс хуже всех») закрываются вообще без шагов и гарантированно цифрой с экрана.
3. **Приоритет источника и его видимость.** Каждый шаг помечен `tool` или `sql`, в развороте размышлений видно, чем получено число. Правило разрешения конфликта: **если метрику даёт инструмент — ответ берётся из инструмента, SQL её не переопределяет.** Тем самым остаточный риск §6 (исполнимый, но логически неверный SQL) перестаёт угрожать ключевым цифрам: `sql` работает только там, где готовой метрики нет и сверять не с чем.

## 5а. Протокол агента

Системный промпт: роль, каталог инструментов, словарь ядра схемы, правила расчёта проекта, описание протокола. Модель на каждом шаге возвращает **один JSON-объект**:

```json
{"thought": "…", "action": "tool", "tool": "leaders", "args": {"by": "dept"}}
{"thought": "…", "action": "schema", "table": "sungero_wf_assignment"}
{"thought": "…", "action": "sql", "query": "SELECT …", "purpose": "…"}
{"thought": "…", "action": "answer", "text": "…"}
```

`thought` обязателен — он же содержимое раскрывающегося блока в чате.

**Почему не штатный tool-calling OpenAI.** У провайдера Ario/vLLM поддержка `tools` не гарантирована, а конфиг умеет переключаться на GigaChat. JSON-протокол одинаково работает на обеих моделях и не зависит от смены провайдера.

**Правила цикла:**

- максимум **5 шагов**, общий бюджет **60 секунд** (расчёт — в §2; с 17.09.2026 — 120 секунд);
- предзагруженные `overview` и `processes` шагов не тратят: их кладёт код до первого вызова модели;
- результат инструмента возвращается модели как JSON сборщика; результат `sql` — таблицей ≤ 50 строк с обрезкой ячеек;
- `thought` держим коротким (просим одно-два предложения): каждый лишний десяток токенов — это треть секунды ожидания;
- при исчерпании бюджета последний вызов просит ответить по уже собранным данным — не обрыв с ошибкой, а ответ с пометкой `truncated: true`;
- если модель вернула не-JSON или неизвестное действие, ей возвращается текст ошибки разбора, и это стоит шага;
- на `answer` цикл завершается.

**Словарь ядра** — ровно те таблицы, которые прототип уже использует (проверено по `Program.cs` 15.09.2026): `sungero_wf_task`, `sungero_wf_assignment`, `sungero_core_recipient`, `sungero_wf_workflowhistory`, `sungero_system_entitytype`, `sungero_content_edoc`, `sungero_recman_taicoassignees`, `sungero_recman_taiparts`, `sungero_recman_taipartscoasgs`, `sungero_wf_processkind`, `sungero_company_jobtitle`, `sungero_parties_counterparty`. Для каждой — назначение, ключевые колонки, связи. Плюс правила: просрочка = `status='InProcess' and deadline < now()`, `Aborted` не считается, уведомления исключаются, дедупликация по `maintask`.

**Справка по таблице** (`action: schema`) берётся из `information_schema.columns` плюс два примера значений на колонку. Закрывает слепоту ручного словаря за пределами ядра, не раздувая промпт.

## 6. Гардрейлы

**Валидатор `SqlGuard.Check`** — по тексту, до выполнения:

1. вырезаются комментарии (`--`, `/* */`), и дальше **исполняется именно очищенный текст** — иначе проверялось бы одно, а в базу уходило другое;
2. ровно один оператор: точка с запятой допускается только хвостовая;
3. текст начинается с `select` или `with`;
4. деней-лист по границам слов: `insert, update, delete, drop, alter, create, truncate, grant, revoke, copy, vacuum, call, do, set, reset, begin, commit, rollback, dblink, pg_read_file, pg_ls_dir, lo_import, lo_export, pg_sleep`;
5. если `limit` отсутствует — запрос оборачивается: `select * from (<запрос>) t limit 200`.

**Исполнитель `SqlGuard.Run`** — отдельное соединение:

```sql
BEGIN; SET TRANSACTION READ ONLY; SET LOCAL statement_timeout = '10s';
<запрос>
ROLLBACK;
```

Read-only транзакция — второй рубеж: даже пропущенная валидатором запись будет отклонена самим PostgreSQL. `statement_timeout` не даёт повесить стенд тяжёлым джойном. Капы на выдачу: 200 строк, 60 колонок, 200 символов на ячейку.

**Остаточный риск.** Исполнимый, но логически неверный SQL даст точное-и-неправильное число. Смягчение: SQL виден пользователю, режим opt-in, надёжный чат по сводке остаётся дефолтом. Отдельная read-only учётка БД остаётся в роадмапе как настоящая граница — сейчас дашборд ходит учёткой с широкими правами (`CLAUDE.md`, «Известные хрупкости»).

## 7. Контракт ответа

`POST /api/ai/sql`, тело `{messages:[{role,content}]}`:

```json
{ "reply": "…",
  "preloaded": ["overview", "processes"],
  "steps": [
    {"n":1, "action":"tool", "thought":"…", "tool":"leaders", "args":{"by":"dept"},
     "rows":21, "ms":5200},
    {"n":2, "action":"sql", "thought":"…", "sql":"SELECT …", "purpose":"…",
     "rows":12, "ms":6100, "cols":["подразделение","просрочено"],
     "preview":[["ДИТ",412],["ДФ",311]]},
    {"n":3, "action":"answer", "thought":"…", "ms":9800}
  ],
  "elapsedMs": 21100, "truncated": false }
```

Поле `action` у каждого шага — это и есть пометка источника: в развороте размышлений видно, что пришло из готовой метрики дашборда, а что модель посчитала запросом.

Ошибка LLM или БД отдаётся полем `error` с русским текстом — как в остальных ИИ-эндпоинтах прототипа, без 500.

`GET /api/ai/sql/check?q=…` → `{ok, reason, effective}`. Только проверка, в базу не ходит. Существует ради тестируемости валидатора.

## 9. Тестирование

- **Валидатор** — новые кейсы в `tests/smoke.py` через `/api/ai/sql/check`: `drop table`, два оператора через `;`, маскировка комментарием, запрос без `limit` (ожидается обёртка), корректный запрос.
- **Исполнитель** — smoke-проверка, что `/api/ai/sql/check` не ходит в базу, и один живой запрос через `/api/ai/sql`.
- **Инструменты** — smoke-проверка, что каждый из девяти вызывается через `ToolRegistry` и отдаёт непустой JSON; и ключевая проверка согласованности: число просрочки, полученное инструментом `overview`, совпадает с тем, что отдаёт `/api/overview` напрямую (иначе весь смысл инструментов теряется).
- **Маршрутизация** — живой прогон вопроса, ответ на который целиком закрывается инструментом («сколько заданий просрочено»): в `steps` не должно быть ни одного `action:"sql"`.
- **Цикл** — живой прогон вопроса, которого нет в готовых метриках: ответ содержит непустой `reply`, хотя бы один `action:"sql"`, `elapsedMs` в пределах бюджета.
- **Фронтенд** — полный прогон `tests/smoke.py` (53 проверки) плюс просмотр всех пяти экранов в браузере до и после.

Ожидаемый результат smoke после работ: `PASS=58+ FAIL=0`.

## 10. Порядок работ

Сначала фронтенд — он изолирован и легко откатывается, после него smoke должен остаться зелёным.

Затем харнесс, снизу вверх: валидатор с тестами → исполнитель → реестр инструментов с проверкой согласованности → словарь схемы → цикл агента → эндпоинты → UI чата.

Реестр инструментов идёт раньше цикла намеренно: он сам по себе даёт полезный результат и проверяется без участия модели.

## 11. Вне объёма (YAGNI)

- Стриминг ответа (переделка транспорта в `HttpListener`) — типичный вопрос около 25 секунд, пока хватает спиннера. Если ожидание покажется долгим на демо — это первый кандидат на доработку.
- Отдельная read-only учётка БД — в роадмап, требует действий на стенде.
- Память диалога между сессиями, история запросов.
- Графики по результату запроса.
- Перестройка каркаса экрана (верхняя навигация вместо сайдбара).
